# 평가 결과

이 프로젝트의 모든 개선은 **같은 시험지로 전/후를 재서** 채택 여부를 정했다.
이 문서는 그 측정 기록이다. 좋아진 것뿐 아니라 **재봤더니 나빠져서 안 넣은 것**도 함께 적는다.

측정 스크립트와 평가셋은 모두 리포에 있어 재실행할 수 있다 (맨 아래 [재현 방법](#재현-방법) 참고).

## 평가 설계 원칙

평가셋을 **데이터 비종속**과 **데이터 종속**으로 나눴다.

- **비종속** (Router / Retrieval) — 시뮬레이션 데이터를 다시 만들어도 그대로 쓸 수 있다. 손으로 작성.
- **종속** (E2E / 멀티턴) — LOT ID가 데이터에 묶여 있다. 시뮬레이터가 심어둔 정답지에서 **자동 생성**한다.

E2E 문항을 손으로 쓰지 않는 이유가 여기 있다. 시뮬 데이터를 재생성하면 LOT ID가 바뀌므로 고정 문항은 곧 어긋난다. `scripts/12_build_e2e_eval.py`가 정답지(`data/eval/simulated_events.json`)를 읽어 문항을 다시 만든다.

## 1. 검색 — 임베딩 파인튜닝 전/후

후공정 도메인 문서로 `BAAI/bge-m3`를 파인튜닝했다. 같은 test 셋 **134문항**으로 비교.

| 지표 | BAAI/bge-m3 (베이스) | postfab-bge-m3-v2 (파인튜닝) | 변화 |
|---|---|---|---|
| Accuracy@1 | 0.7687 | **0.8433** | +7.5%p |
| Accuracy@3 | 0.8881 | **0.9701** | +8.2%p |
| Accuracy@5 | 0.9328 | **0.9851** | +5.2%p |
| NDCG@10 | 0.8689 | **0.9252** | +5.6%p |

### 문서 유형별 분해

| 유형 | n | Accuracy@1 | Accuracy@3 | NDCG@10 |
|---|---|---|---|---|
| 용어 카드 (glossary_card) | 74 | 0.757 → **0.905** | 0.878 → **1.000** | 0.872 → **0.963** |
| 본문 청크 (article_chunk) | 60 | 0.783 → 0.767 | 0.900 → **0.933** | 0.865 → **0.878** |

**이득은 대부분 용어 카드에서 나왔다.** 도메인 용어(FDC, EMC, Incomplete Fill 등)를 베이스 모델이 잘 구분하지 못하던 것이 파인튜닝으로 해결돼 Accuracy@3가 만점이 됐다.

반면 **본문 청크의 Accuracy@1은 0.783 → 0.767로 오히려 소폭 하락했다.** 청크는 여러 개가 서로 비슷해 1등을 가리기 어려운 성격이고, 파인튜닝이 용어 쪽으로 표현을 당긴 영향으로 보인다. Accuracy@3·NDCG@10은 개선됐고 실제 파이프라인은 상위 3~5개를 컨텍스트로 넘기므로 실사용에는 영향이 없다고 판단해 채택했다.

### 질문 유형별

| 유형 | n | Accuracy@1 | NDCG@10 |
|---|---|---|---|
| term (용어) | 74 | 0.757 → **0.905** | 0.872 → **0.963** |
| concept (개념) | 36 | 0.750 → 0.722 | 0.840 → **0.848** |
| judgment (판정) | 16 | 1.000 → 1.000 | 1.000 → 1.000 |
| flow (흐름/절차) | 8 | 0.500 → 0.500 | 0.704 → **0.769** |

**flow 유형이 가장 약하다** (Accuracy@1 0.5). "A 다음에 뭐 하냐" 같은 절차 질문은 정답 청크가 하나로 특정되지 않고 여러 문서에 흩어져 있어서다. 문항 수가 8개뿐이라 통계적으로 단정하긴 어렵지만, 개선 여지가 남은 지점으로 기록해 둔다.

## 2. BM25 하이브리드 검색 — 측정 후 미채택

키워드 검색(BM25)과 벡터 검색을 RRF로 결합하면 나아질 것으로 보고 구현했다(`src/rag/bm25_index.py`). **같은 시험지로 재봤더니 전체적으로 나빠져서 넣지 않았다.**

| 지표 | 벡터 단독 | +BM25 하이브리드 | 변화 |
|---|---|---|---|
| Accuracy@1 | **0.8433** | 0.8209 | −2.2%p |
| Accuracy@3 | **0.9701** | 0.9254 | −4.5%p |
| Accuracy@5 | **0.9851** | 0.9701 | −1.5%p |
| NDCG@10 | **0.9252** | 0.9098 | −1.5%p |

### 왜 나빠졌나 — 유형별로 보면 명확하다

| 유형 | n | Accuracy@3 (벡터) | Accuracy@3 (하이브리드) |
|---|---|---|---|
| 용어 카드 | 74 | **1.000** | 0.905 (−9.5%p) |
| 본문 청크 | 60 | 0.933 | **0.950** (+1.7%p) |

**본문 청크는 실제로 좋아졌다.** 긴 문서에서 특정 키워드를 찾는 건 BM25가 잘하는 일이다.

문제는 용어 카드였다. 파인튜닝 + 정확일치 로직으로 이미 만점(1.000)이라 BM25가 **더할 게 없고 노이즈만 됐다.** 그런데 카드가 데이터셋의 절반 이상(74/134)이라 전체 평균은 순손실이 됐다.

**결론: 프로덕션 미반영.** `retriever.py`의 기본 동작은 벡터 단독을 유지한다. 카드/청크에 선택 적용하는 튜닝도 가능하지만, 이미 Accuracy@3 0.97인 구간에서 복잡도를 늘릴 이유가 없다고 판단했다. 실험 코드와 결과 파일(`data/eval/retrieval_postfab-bge-m3-v2_test_hybrid.json`)은 기록으로 남겨 뒀다.

> 이 항목을 지우지 않고 남겨 둔 이유: 무엇을 넣었는지보다 **무엇을 재보고 뺐는지**가 판단 근거를 더 잘 보여준다고 생각한다.

## 3. Router — intent 분류

4개 intent(`knowledge` / `data` / `root_cause` / `out_of_scope`)를 얼마나 정확히 나누는지 측정. 손으로 쓴 **26문항**(멀티턴 맥락 3문항 포함).

**결과: 26/26 (100%)**

측정하다가 **그래프 배선 버그를 발견했다.** Router 프롬프트에는 `out_of_scope`가 있었는데 `route_by_intent`가 그 분기를 무시하고 전부 `knowledge`로 흘려보내고 있었다. 즉 범위 밖 질문에도 RAG를 태워 억지 답을 만들던 상태였다. `out_of_scope_node`를 신설해 LLM 호출 없이 정중히 거절하도록 고쳤다.

> 평가셋을 만들지 않았으면 못 찾았을 버그다. 겉으로는 답이 나오고 있었기 때문이다.

## 5. E2E 원인 분석

Router → Planner → Data → Knowledge → Report **전 구간**을 태우고 **최종 리포트 본문**에 정답이 있는지 본다. 시뮬레이터가 심어둔 이상 사건에서 자동 생성한 **36문항** (recipe_spec_violation 12 / strip_pattern 12 / eqp_degradation 6 / sudden_drop 6).

### 지표 4종

| 지표 | 결과 |
|---|---|
| intent 정확도 | 36/36 (100%) |
| **지식베이스 인용률** | 36/36 (100%) |
| 정답 키워드 재현 | 107/108 (99.1%) |
| **문항 성공률** (부분점수 없음) | **35/36 (97.2%)** |
| LLM 의미 채점 | 36/36 전 항목 통과 |

유형별: recipe_spec_violation 12/12, eqp_degradation 6/6, sudden_drop 6/6, strip_pattern 11/12.

**지식베이스 인용률을 따로 두는 이유**가 이 평가의 핵심이다. 리포트에 그럴듯한 원인 설명이 있어도 그게 RAG에서 온 것인지 LLM 내부 지식인지 알 수 없다. 실제로 이 파이프라인이 **후자였던 적이 있다** — 리포트는 멀쩡해 보였지만 검색된 문서를 실제로 쓰고 있지 않았다. 그래서 "해당 사건의 대응 문서가 검색 컨텍스트에 실제로 들어왔는가"를 별도 지표로 뒀다.

### 이 숫자에 붙는 단서 (중요)

**97.2%는 첫 신뢰 가능한 기준선이다.** 그 전 1차 실행은 66.7%였지만 **두 값을 직접 비교하면 안 된다.** 그 사이 채점기를 3번 고쳤기 때문이다.

1차 66.7%의 원인은 시스템이 아니라 채점기였다.

| # | 버그 | 실제 내용 |
|---|---|---|
| ① | emap 패턴 키 오타 | 정답지 키가 카드 제목과 한 글자 달라 인용률 오판정. **카드는 처음부터 정상 검색되고 있었다.** |
| ② | 키워드를 성격 구분 없이 정확일치 비교 | 기계 식별자(`ML001`, `MOLD_TEMP_3`)는 정확 비교가 맞지만, 한글 라벨("가장자리 분포" ↔ "가장자리 집중")은 모델이 바꿔 쓴다 |
| ③ | 식별자 안쪽 마크다운 | 리포트가 `260329_STRSIM00147_**01**`처럼 볼드를 넣어 문자열 비교 실패 |

**채점기 수정 3번이 모두 점수를 올렸다.** 이 패턴을 계속하면 의미 없는 100%가 된다. 그래서 정당화 기준을 점수가 아니라 ①원칙(마크다운은 표현이지 내용이 아님) ②오탐 검사 통과로 뒀다. 4번째가 나오면 채점기가 아니라 평가 설계를 의심하기로 했다.

### 실행 편차 — `temperature`가 범인이었다

1차 때는 **실패한 문항을 그냥 재실행하면 통과하는** 일이 있었다. 5개 에이전트가 전부 `temperature` 기본값(1.0 = 최대 무작위)으로 돌고 있었기 때문이다. 5개 에이전트와 LLM 채점기에 `temperature=0`을 지정한 뒤에야 **실패 문항이 재실행에서 동일하게 재현**되는 것을 확인했고, 그때 처음으로 단일 실행 값을 기준선으로 쓸 수 있게 됐다.

같이 고친 것: `report_agent`의 `max_tokens` 2048 → 4096. 2048에서 리포트가 '5. 권장 조치' 중간에 잘리고 있었다.

### 비용

1문항 약 **$0.071** (Haiku 5콜 + Sonnet 1콜). 36문항 전체 실행 약 **$2.8**. Report Agent(Sonnet)가 비용의 62%.

## 6. 멀티턴

대화 5개 / 14턴. **intent만 재면 부족해서 도구 인자와 lot_id까지 채점한다** — `data`로 잘 분류돼도 `eqp_id`를 안 채우면 답이 쓸모없기 때문이다.

| 지표 | 적용 전 | 적용 후 |
|---|---|---|
| 턴 통과율 | 12/14 | **14/14 (100%)** |
| 대화 통과율 | 4/5 | **5/5 (100%)** |
| intent 정확도 | — | 100% |
| 지시어 해석 | — | 100% |

### 측정으로 찾은 문제 두 개

**① RAG 검색어에 지시어가 그대로 들어가고 있었다.** `knowledge_agent.answer()`가 질문 원문을 `retrieve()`에 넘긴다. 검색은 대화를 못 보므로 "그게 뭔데?"로 검색하면 엉뚱한 카드가 나오고, Knowledge Agent는 (지어내지 말라는 지시를 지켜) 되묻는다. **시스템은 정상이고 검색어만 틀린 것이었다.**

→ Router 앞에 질문 재작성기(`src/agents/rewriter_agent.py`)를 넣었다. history가 없으면 아예 호출하지 않아 단일 질문에는 위험이 0이고, 결과가 길거나 여러 줄이거나 API 오류면 원문을 쓴다. 재작성기 단독 평가 **9/9** (풀어야 할 것 5 + 건드리면 안 되는 것 4).

**② history가 무제한 누적되고 있었다.** 원래 계획에 없던 항목인데 실측으로 발견했다 — 8턴 만에 Router 입력이 1,703 → 6,920 토큰(4배). 리포트 1건이 +2,500 토큰이고 Data Agent는 agentic loop라 도구 호출마다 전체를 재전송한다.

→ `compact_history()`를 `workflow.run()`에 두어 서버측 한 곳에서 처리(웹/Streamlit/API에 동시 적용). **리포트는 '요약' 섹션만 남기고**(3,189자 → 291자), **표는 그대로 둔다** — "첫번째 LOT"이 앞 턴의 표를 가리키므로 자르면 멀티턴이 깨진다. 최근 6턴 상한.

**결과: 8턴 기준 9,380자 → 2,616자 (72% 감소).**

### 회귀 없음

멀티턴 적용 후 기존 평가 전부 재실행: Router 26/26, Data Agent 18/18, 데모 시나리오 8/8.


## 한계

정직하게 적어 둔다.

- **E2E 36문항은 시뮬레이션 데이터 기반이다.** 실제 현장 데이터가 아니므로 "97.2%"는 이 시험지 안에서의 값이다.
- **`temperature=0`이어도 완전 결정론은 아니다.** 재실행 시 소수 문항이 흔들릴 수 있다.
- **채점기를 3번 고쳤고 3번 다 점수가 올랐다.** 각 수정에 원칙과 오탐 검사를 붙였지만, 이 방향의 수정은 계속하면 위험하다.
- **flow 유형 검색 정확도(Accuracy@1 0.5)가 낮다.** 문항이 8개뿐이라 단정할 수 없고, 개선 과제로 남아 있다.
- **평가셋 규모가 크지 않다.** Router 26 / Data Agent 10 / E2E 36 / 멀티턴 14턴.
